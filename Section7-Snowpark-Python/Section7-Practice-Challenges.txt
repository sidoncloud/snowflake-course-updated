CHALLENGE 1
THE 6 AM DASHBOARD
Concepts: Snowpark DataFrame API, Python stored procedures, Tasks
Covers lectures L1, L2, L5, L6

THE PROBLEM

You have joined an online retailer. Every morning at 6 AM the leadership team
opens a dashboard showing yesterday's revenue, the top selling products, and
which customers are worth the most. Today an analyst rebuilds that dashboard by
hand, every single day, and it is usually late.

Your job is to replace that person with a pipeline. Everything must run inside
Snowflake, written in Python, and it must run itself on a schedule.

THE DATASET

Four tables, all provided with the lab.

customers.csv, 500 rows
  customer_id, first_name, last_name, email, phone, date_of_birth, gender,
  city, state, country, registration_date, acquisition_channel, is_active

orders.csv, 2,793 rows
  order_id, customer_id, order_date, order_status, shipping_address,
  shipping_city, shipping_country, payment_method, subtotal, discount_amount,
  shipping_cost, tax_amount, total_amount, created_at

order_items.csv, 6,384 rows
  order_item_id, order_id, product_id, quantity, unit_price,
  discount_percent, line_total

products.csv, 92 rows
  product_id, product_name, category, subcategory, brand, unit_price,
  cost_price, stock_quantity, weight_kg, created_at, is_active

WHAT YOU MUST BUILD

1. A customer analytics table. For every customer, compute lifetime value,
   order count, average order value, and days since their last order. Then
   segment them into tiers based on what you find.

2. A product performance table. Rank products by revenue within each category.
   You have both unit_price and cost_price, so calculate real margin, not just
   revenue. Ranking within a group is a hint: reach for a window function.

3. A daily sales summary table. One row per day, with revenue, order count,
   and units sold.

4. Write all three using the Snowpark DataFrame API. No raw SQL strings.

5. Deploy each transformation as a permanent Python stored procedure.

6. Schedule them with Snowflake Tasks so the whole thing runs before 6 AM,
   with the summary task running only after the other two finish.

CHECK YOURSELF

  Can you explain which parts of your DataFrame code ran in Snowflake and
  which ran on your machine?
  Does your pipeline produce the same result if it runs twice in a row?
  What happens to your task chain if the first procedure fails?

SOLUTION
https://cognifydata.com/labs/ecommerce-order-analytics
10 tasks, about 90 minutes, free


CHALLENGE 2
PRICE THE HOUSE
Concepts: Snowpark ML, feature engineering, Model Registry, SQL inference
Covers lectures L7, L9, L10

THE PROBLEM

A property listings site wants an instant price estimate the moment a seller
posts a new listing. The data science team has no infrastructure and no
appetite for one. Everything has to live in Snowflake, and the application
team must be able to score a property with plain SQL.

You are handed 5,000 historical sales. Build the model, and make it callable.

THE DATASET

properties.csv, 5,000 rows, 21 columns

  property_id, city, state, zip_code, property_type, bedrooms, bathrooms,
  sqft, lot_size_sqft, year_built, stories, garage_spaces, has_pool,
  has_basement, has_fireplace, condition, neighborhood_score, school_rating,
  walk_score, listing_date, sale_price

sale_price is your target. Everything else is fair game as a feature.

WHAT YOU MUST BUILD

1. Separate schemas for raw data, features, and models. Keep them apart.

2. Engineered features. year_built is not useful as is, property age is.
   Bedrooms and bathrooms separately are weaker than total rooms. The
   categorical columns need encoding before a model will accept them.

3. Three trained models using Snowpark ML: Linear Regression, Random Forest,
   and Gradient Boosting.

4. A proper evaluation. RMSE, MAE and R squared on a held out test set, not on
   the data you trained on. Pick a winner and be able to defend the choice.

5. The winning model registered in the Snowflake Model Registry.

6. A SQL query that takes one new property and returns a predicted price.

CHECK YOURSELF

  Why does the Model Registry matter here? What would break without it?
  Your training features and your inference features have to match exactly.
  How would you catch it if they silently drifted apart?

SOLUTION
https://cognifydata.com/labs/property-price-prediction-snowpark-ml
8 tasks, about 75 minutes, free


CHALLENGE 3
CATCH THE FAILURE BEFORE IT HAPPENS
Concepts: time windowed features, model versioning, scheduled batch inference
Covers lecture L11, and goes further

THE PROBLEM

A factory floor has 100 machines wired with sensors. When one fails without
warning, the line stops and it costs thousands of dollars an hour. You have
the raw telemetry and a maintenance log going back months.

Predict which machines are heading for a failure in the next seven days, and
put the scoring on a schedule so the maintenance team gets a fresh list every
morning without asking anyone.

This is the hardest of the three. Attempt it after the first two.

THE DATASET

sensor_readings.csv, 144,000 rows
  reading_id, equipment_id, timestamp, temperature_c, vibration_mm_s,
  pressure_psi, rpm, humidity_pct, power_consumption_kw, oil_level_pct,
  is_failure_within_7d

equipment.csv, 100 rows
  equipment_id, equipment_type, manufacturer, install_date,
  last_maintenance_date, location

maintenance_logs.csv, 134 rows
  log_id, equipment_id, maintenance_date, maintenance_type, failure_type,
  downtime_hours, cost_usd, description

is_failure_within_7d is your label.

WHAT YOU MUST BUILD

1. Time windowed features from the raw readings. A single temperature reading
   tells you almost nothing. A rolling average, a rolling maximum, and the rate
   of change over a window tell you a great deal.

2. A training set that does not leak. Think carefully about how you split it
   when every row has a timestamp.

3. Trained and compared classification models using Snowpark ML.

4. The best model registered, with a version, in the Model Registry.

5. Batch inference through the Registry against fresh readings.

6. A Snowflake Task that reruns the scoring on a schedule.

CHECK YOURSELF

  Only a small fraction of rows are failures. Does accuracy mean anything
  here, and if not, what should you measure instead?
  You register version 1 today. Next month you retrain. How do you ship
  version 2 without breaking whatever is already calling the model?

SOLUTION
https://cognifydata.com/labs/predictive-maintenance-pipeline
10 tasks, about 90 minutes, advanced


A NOTE ON THE SOLUTIONS

The labs solve these problems with the Python written inside stored procedure
bodies, which is slightly different from the standalone script style I use in
the course videos. The Snowpark API calls are identical. Seeing both patterns
is useful, because you will meet both in real projects.


HOW TO GET THE MOST OUT OF THESE

Do not open the solution first. Read the problem, open a worksheet, and get
something wrong for twenty minutes. That struggle is the entire point. The
solution will still be there afterwards, and it will mean more.
